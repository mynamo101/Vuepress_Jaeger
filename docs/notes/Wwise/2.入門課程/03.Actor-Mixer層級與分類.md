## 一、為什麼需要層級結構？

### 🗄️ 層級就像你的檔案櫃系統

**生活化比喻**：
- **沒有層級**：所有衣服堆在一個大箱子 = 找一件 T-shirt 要翻 10 分鐘
- **有了層級**：上衣 / 褲子 / 外套分層 = 3 秒找到想要的

### 層級存在的四大價值

| 功能     | 說明                              | 實際範例                     |
| -------- | --------------------------------- | ---------------------------- |
| 結構清晰 | 找得到、路徑可預測                | 腳步音不會跟 UI 音效混在一起 |
| 設定繼承 | Volume / Attenuation 可往下層傳遞 | 整類環境音一次降低 2dB       |
| 混音控制 | 高層節點可直接 Solo / Mute        | 快速對比不同音效層的效果     |
| 團隊協作 | Work Unit 分拆避免版本控制衝突    | 角色音效 / 音樂由不同人維護  |

::: tip 💡 設定繼承的魔力
在父層級設定 Volume -3dB，所有子物件自動繼承！
不用一個一個調整 100 個音效檔案。
:::

## 二、新手常犯的三大錯誤

### ❌ 錯誤 1：層級過深（超過 5 層）

**問題範例**：
```
SFX → Characters → Player → Actions → Combat → Melee → Sword → Light_Attack
```
這樣的結構有 **8 層**，查找和維護都很痛苦。

**改善建議**：
```
SFX → Characters → Player_Combat → Sword_Light
```
控制在 **3-5 層**，保持扁平化。

### ❌ 錯誤 2：完全鏡像檔案系統

**問題說明**：
有些人會把硬碟的檔案資料夾結構完全複製到 Wwise 中。

**為什麼不好？**
- 檔案系統是「儲存邏輯」（按製作時間、素材來源）
- Wwise 需要「遊戲邏輯」（按功能、混音需求）

**折衷方案**：
以「功能分類 + 混音需求」為主，適度參考檔案結構。

### ❌ 錯誤 3：混音分類與功能分類混淆

**問題範例**：
把 Music 和 Ambience 放在同一層級，但它們的混音需求完全不同。

**改善建議**：
- Actor-Mixer Hierarchy：功能分類（SFX / Music / VO / Ambience / UI）
- Master-Mixer Hierarchy (Bus)：混音分類（對應功能分類）
- 兩者要能對齊，但不要混在一起

## 三、命名規範的黃金法則

### 📝 推薦的命名慣例

| 物件類型          | 命名規範               | 範例                     |
| ----------------- | ---------------------- | ------------------------ |
| Actor-Mixer Group | PascalCase（大寫開頭） | `Footsteps`、`WeaponSFX` |
| Random Container  | PascalCase + Container | `Footsteps_Container`    |
| Sound SFX         | 描述性 + 細節          | `Footstep_Grass_Soft_01` |
| Event             | 動詞 + 底線分隔        | `Play_Footstep`          |

### ✅ 好的命名範例

```
SFX
├─ Characters
│  ├─ Player_Footsteps
│  │  ├─ Footstep_Grass_01
│  │  ├─ Footstep_Grass_02
│  │  └─ Footstep_Stone_01
│  └─ Player_Combat
│     ├─ Sword_Swing_Light
│     └─ Sword_Hit_Metal
```

### ❌ 不好的命名範例

```
sfx
├─ char
│  ├─ plyr_footsteps
│  │  ├─ fs_grass_v1_final_FINAL
│  │  ├─ footstep草地_2
│  │  └─ temp_test_123
```

::: warning 🚫 命名禁忌
1. **避免版本號**：不要用 `_v1`、`_final`、`_FINAL2`
2. **避免中文**：某些系統會有編碼問題
3. **避免縮寫過度**：`fs_gr_01` 別人看不懂
4. **保持一致性**：全團隊用同一套規範
:::

## 四、Work Units 分拆策略

### 🗂️ 什麼是 Work Unit？

Work Unit 就像是「子專案檔案」，可以獨立編輯，避免多人同時修改同一個檔案造成衝突。

### 推薦的分拆策略

| 模組類型 | 建議 Work Unit | 分拆原因                   |
| -------- | -------------- | -------------------------- |
| 角色音效 | `Characters`   | 變動頻繁，需要獨立維護     |
| 環境音效 | `Ambience`     | 體量大、會長期補充素材     |
| 音樂     | `Music`        | 較少改動、易於單獨發布更新 |
| UI 音效  | `UI`           | 小而集中，獨立測試方便     |
| 語音對話 | `VO`           | 需要本地化、有獨立流程     |

### 實際操作：建立新的 Work Unit

1. **在 Actor-Mixer Hierarchy 中**
2. **右鍵 Default Work Unit** → New Child → Work Unit
3. **命名**：`Characters_WU`（加 _WU 後綴方便識別）
4. **移動素材**：將相關的 Actor-Mixer Group 拖入新 Work Unit

::: tip 💡 Work Unit 最佳實踐
- 一個 Work Unit 不要太大（超過 100 個物件考慮再分拆）
- 按功能模組分，不要按人員分
- 定期檢查是否需要重新整理
:::

## 五、實戰練習：建立專案骨架

現在我們來建立一個標準的 Wwise 專案骨架結構。

### 🏗️ 推薦的基礎架構

```
Actor-Mixer Hierarchy
├─ SFX
│  ├─ Characters
│  │  ├─ Player
│  │  │  ├─ Footsteps
│  │  │  └─ Combat
│  │  └─ Enemies
│  ├─ Weapons
│  │  ├─ Melee
│  │  └─ Ranged
│  └─ Environment
│     ├─ Interactive_Objects
│     └─ Destruction
├─ Ambience
│  ├─ Outdoor
│  │  ├─ Forest
│  │  └─ City
│  └─ Indoor
│     ├─ Room_Small
│     └─ Room_Large
├─ UI
│  ├─ Menu
│  ├─ HUD
│  └─ Notifications
├─ Music
│  ├─ MainTheme
│  ├─ Combat
│  └─ Ambient
└─ VO
   ├─ Player
   ├─ NPCs
   └─ Enemies
```

### 實際操作步驟

#### Step 1: 建立主要分類
1. 在 **Actor-Mixer Hierarchy** 中
2. 右鍵 **Default Work Unit** → New Child → **Actor-Mixer Hierarchy**
3. 依序建立：`SFX`、`Ambience`、`UI`、`Music`、`VO`

#### Step 2: 建立 SFX 子分類
1. 右鍵 `SFX` → New Child → Actor-Mixer Hierarchy
2. 建立：`Characters`、`Weapons`、`Environment`

#### Step 3: 建立 Characters 細分
1. 右鍵 `Characters` → New Child → Actor-Mixer Hierarchy
2. 建立：`Player`、`Enemies`
3. 在 `Player` 下建立：`Footsteps`、`Combat`

#### Step 4: 移動之前的素材
將之前建立的 `Footsteps` Random Container 移動到 `SFX → Characters → Player → Footsteps` 下。

::: tip 💡 建立骨架的時機
**專案初期就要規劃好！**
不要等素材多了才整理，那會非常痛苦。
:::

## 六、確保 Bus 層級與 Actor-Mixer 對齊

### 🔗 為什麼要對齊？

Actor-Mixer 管理「素材組織」，Bus 管理「混音路由」。
兩者要能對應，才能快速定位問題。

### 推薦的對應關係

| Actor-Mixer 層級 | 對應的 Bus             |
| ---------------- | ---------------------- |
| SFX              | Bus_SFX (或直接叫 SFX) |
| Music            | Bus_Music              |
| VO               | Bus_VO                 |
| Ambience         | Bus_Ambience           |
| UI               | Bus_UI                 |

### 快速檢查方法
1. 選中 `SFX` 群組
2. 查看 Property Editor → **Output Bus**
3. 確認路由到 `Bus_SFX`（而非直接到 Master Audio Bus）

::: warning ⚠️ 常見錯誤
不要讓所有聲音都直接輸出到 Master Audio Bus！
這樣無法做分層混音控制。
:::

## 七、可維護性與擴展性思路

### 🔄 隨著專案成長的調整策略

#### 初期（100 個音效以內）
- 保持扁平化，3-4 層即可
- 只建立核心分類

#### 中期（100-500 個音效）
- 開始細分 Work Units
- 根據實際需求增加子分類

#### 後期（500+ 個音效）
- 考慮按關卡 / 場景分拆
- 建立專門的命名與組織文檔

### 📋 定期維護檢查清單

- [ ] 是否有孤立的素材沒有歸類？
- [ ] 命名規範是否一致？
- [ ] Work Units 是否需要重新分拆？
- [ ] 是否有重複或冗餘的結構？

## 八、常見問題與解決方案

### 💡 FAQ

| 🤔 問題                   | 🔍 原因分析       | ✨ 解決方案                              |
| -------------------------- | ------------------ | ---------------------------------------- |
| 找不到某個音效在哪裡       | 分類邏輯不清晰     | 建立清晰的分類文檔，團隊共享             |
| 修改一個設定影響了所有音效 | 不理解繼承機制     | 在子層級覆寫設定，而非修改父層級         |
| 多人協作時經常有衝突       | Work Unit 沒有分拆 | 按功能模組分拆 Work Units                |
| 層級太深找東西很慢         | 過度細分           | 合併不必要的中間層級，保持 3-5 層        |
| 不知道該放在 SFX 還是 UI   | 分類標準不明確     | 問自己：這是「遊戲玩法」還是「界面互動」 |
