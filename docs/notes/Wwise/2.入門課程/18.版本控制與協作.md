::: tip 團隊協作，穩健開發
Wwise 專案越大，團隊協作越重要。版本控制不只是「備份」，更是多人協作、避免衝突、追蹤歷史的關鍵工具。本課將帶你掌握 Wwise 與版本控制的最佳實踐。
:::

## 🎯 本節你會收穫
- 🗂️ 理解 Wwise 專案檔案的版本控制策略
- 🔄 學會多人協作時的衝突處理與合併
- 📝 掌握 .gitignore、LFS、大型檔案管理
- 🚦 SoundBank 與原始音檔的管理原則
- 💡 團隊溝通與官方最佳實踐

## Wwise 專案檔案管理

### 推薦加入版本控制的檔案
| 類型       | 說明               |
| ---------- | ------------------ |
| .wproj     | 專案主檔案         |
| .wwu       | Work Unit 檔案     |
| Originals/ | 原始音訊素材資料夾 |

### 建議排除的檔案
| 類型                         | 說明                       |
| ---------------------------- | -------------------------- |
| .backup/                     | 升級時產生，版本控制可回滾 |
| .cache/                      | 本地暫存，勿加入           |
| .prof                        | 分析檔案，非專案資料       |
| .validationcache             | 由 .wwu 產生，可排除       |
| .wsettings                   | 本地用戶設定               |
| IncrementalSoundBankData.xml | SoundBank 狀態追蹤檔       |

::: tip .gitignore 範例
```
.backup*
.cache*
*.akd
*.prof
*.validationcache
*.wsettings
IncrementalSoundBankData.xml
```
:::

## 大型檔案管理與 LFS

- 建議使用 Git LFS 管理大型二進位檔案（如 .wav、.aif、.png、.jpg）。
- `.gitattributes` 範例：
```
*.wav filter=lfs diff=lfs merge=lfs -text
*.aif filter=lfs diff=lfs merge=lfs -text
*.png filter=lfs diff=lfs merge=lfs -text
*.jpg filter=lfs diff=lfs merge=lfs -text
```

## 多人協作與合併衝突

### 避免衝突的最佳實踐
- 按功能模組分拆 Work Unit，確保不同人員負責不同部分。
- 定期同步版本控制系統中的最新變更。

### 處理衝突
- 多人同時修改同一 Work Unit 時，版本控制系統（如 Perforce）會提示合併衝突。
- 使用版本控制工具的合併功能，手動檢查並解決衝突。
- 合併後請測試 Work Unit 能正常加載。

## Wwise 與版本控制系統整合

### 支援的系統
- Wwise 支援 Perforce、Subversion，並有內建插件。
- 其他系統需支援第三方 API 整合。

### 啟用插件
1. Wwise → Project > Source Control > Connect
2. 選擇版本控制系統（如 Perforce）
3. 配置伺服器、用戶名、密碼

### 常用操作
- **簽出檔案**：右鍵 Work Unit → Check Out
- **提交變更**：右鍵 → Check In，填寫訊息
- **檢視狀態**：Project Explorer 查看簽出/未提交狀態

## SoundBank 檔案管理

- SoundBank 可由專案重新產生，通常不需加入版本控制。
- 若團隊有非 Wwise 使用者需測試音效，可將 soundbanks/ 路徑下的 .bnk、.wem 檔案加入版本控制。
- 若多人同時加入 SoundBank，易產生不同步問題，建議統一管理。

## 行尾設定與專案一致性

- Wwise 預設以 LF 儲存檔案，可在專案設定中改為 CRLF。
- 團隊需統一行尾規則，避免合併衝突。

## FAQ 常見問題
| 問題         | 原因                       | 解法                           |
| ------------ | -------------------------- | ------------------------------ |
| 無法簽出檔案 | 檔案已被其他人簽出         | 聯繫對方協調提交或等待簽入     |
| 合併衝突     | 多人同時修改同一 Work Unit | 使用版本控制工具手動合併並測試 |
| 插件無法連接 | 配置錯誤或伺服器不可用     | 檢查伺服器地址與網路連接       |

## 官方最佳實踐全攻略

### 1. 專案規劃
- **分拆 Work Unit**：大型專案請將資料分拆到多個 Work Unit，避免全部集中在 Default Work Unit，提升效能並減少合併衝突。
- **指定管理者**：全域 Default Work Unit 建議由專人負責，確保重要元素變更有專人把關。

### 2. 基本工作流程
- **全域元素管理**：如 State、Game Parameter 等全域元素，變更前請通知團隊，要求大家先提交並同步，避免大範圍衝突。
- **變更流程**：
  1. 通知團隊有全域元素變更
  2. 請所有人提交並同步
  3. 你再提交變更
  4. 團隊再同步新檔案
- **檢查檔案狀態**：開始編輯前，請用 File Manager 檢查檔案是否唯讀，唯讀檔案無法儲存。
- **定期備份本地檔案**：中央倉庫有排程備份，但本地檔案需自行備份，重大修改後務必備份。
- **Integrity Report**：提交前產生 Integrity Report，確保專案無錯誤。

### 3. 同步與協作
- **每次工作前先同步**：開始新工作階段前，先同步最新檔案。
- **同步前關閉 Wwise**：若未用插件，請先關閉 Wwise 再同步，避免記憶體與磁碟版本不一致。
- **用插件同步**：若用 Source Control 插件，系統會自動提示重新載入最新版本。

### 4. 提交與註解
- **常提交、小範圍**：有大變動時請常提交，讓團隊及時獲得最新內容，避免衝突。
- **有用註解**：每次提交請詳細描述變更內容，方便團隊追蹤。

### 5. 系統理解
- **熟悉版本控制系統**：使用前請先了解系統運作原理，避免誤操作。

### 6. 專案一致性與安全
- **熟悉 Wwise XML 結構**：合併前請先了解 XML 結構，必要時手動修改 XML，修改後請用 Wwise 開啟確認。
- **刪除未使用檔案**：File Manager 標記為 Unused 的檔案，刪除前請重啟專案，確保資訊最新。

### 7. 溝通與團隊協作
- **頻繁公開溝通**：團隊協作時，請保持頻繁且公開的溝通，遇到全域變更或大規模調整時，務必通知所有成員。
- **協作流程**：如需變更影響他人 Work Unit，請先通知、等大家提交後再進行。

### 8. 檔案管理與 SoundBank
- **SoundBank 設定**：SoundBank 在 Project Explorer 的 SoundBanks 標籤下以 Work Unit 管理，建議用 Container 分類，減少頻繁變動。
- **Generated SoundBanks**：由 Wwise 產生，預設在 GeneratedSoundBanks 資料夾，建議排除於版本控制。

::: tip 官方建議
- 分拆 Work Unit、指定管理者、全域元素變更流程、定期備份、Integrity Report、同步前關閉 Wwise、常提交與註解、熟悉 XML 結構、頻繁溝通、SoundBank 管理。
- 詳細內容請參考 [Source control tips and best practices](https://www.audiokinetic.com/library/2024.1.8_8898/?source=Help&id=workgroup_tips_best_practices)
:::
